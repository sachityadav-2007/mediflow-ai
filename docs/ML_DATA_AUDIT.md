## 1. Executive Summary & Scientific Honesty Statement

In strict compliance with medical informatics AI governance, healthcare software safety, and institutional research ethics:

> [!IMPORTANT]
> **Core Audit Finding:**  
> A genuine Machine Learning model requires **ground-truth target labels** generated by authentic operational events.  
> The existing MediFlow AI PostgreSQL database contains **76 appointment bookings**, **9 doctor profiles**, **17 doctor attendance records**, and **121 presence logs**.  
> However:
> 1. In the `appointments` table, the `checkedInAt` field is `NULL` across all 76 historical records ($100\%$ missing).
> 2. The `appointments` table historically lacked dedicated timestamp columns for `consultationStartedAt` and `consultationCompletedAt`.
> 3. Consequently, **ground-truth patient waiting times** ($\text{consultation\_start} - \text{check\_in}$) and **ground-truth consultation durations** ($\text{consultation\_end} - \text{consultation\_start}$) are **NOT present in historical database records**.
> 4. To claim that a waiting-time or duration model is trained on real hospital data would constitute academic fabrication.
> 5. Therefore, in MediFlow AI 2.0, the training pipelines, feature engineering, and model architectures for these targets are **FULLY IMPLEMENTED**, evaluated on clearly labeled development verification datasets, and exposed via FastAPI with the explicit production status: `INSUFFICIENT_DATA`.
> 6. We establish a prospective data capture mechanism within the Prisma schema to begin accumulating genuine ground-truth timestamps starting immediately.

### 3.1 Model 1: Patient Waiting Time Prediction
- **Required Target Definition:**  
  $$W_i = t_{\text{consultation\_start}} - t_{\text{patient\_check\_in}}$$
- **Database Findings:**  
  The `appointments` table contained no recorded `checkedInAt` values for historical appointments, and no column for consultation start timestamp.
- **Data Quality Verdict:**  
  **INSUFFICIENT HISTORICAL DATA.** Training an ML model directly on this database without labels is mathematically impossible without synthesizing labels.
- **Remediation Strategy:**  
  1. Build the full scikit-learn regression pipeline (`RandomForestRegressor`, `GradientBoostingRegressor`, `DummyRegressor`).
  2. Implement an automated development pipeline validation harness with clearly designated `SYNTHETIC_DEVELOPMENT` data to verify code correctness, hyperparameter tuning, and serialization.
  3. Deploy the FastAPI service to return `status: "insufficient_data"` on live queries until real operational check-in events accumulate.

### 3.2 Model 2: Doctor Availability and Delay Prediction
- **Required Target Definition:**  
  $$\text{Available}_i \in \{0, 1\}, \quad \text{Delay}_i = \mathbb{I}(t_{\text{actual\_arrival}} > t_{\text{scheduled\_slot}} + 15\text{ min})$$
- **Database Findings:**  
  The `doctor_attendances` table holds 17 records across 9 doctors ($\approx 1.8$ attendance sessions per doctor). The `presence_logs` table contains 121 state transitions.
- **Data Quality Verdict:**  
  **INSUFFICIENT SAMPLE SIZE.** Statistical learning theory demonstrates that fitting a classifier on 17 instances across 9 distinct classes results in near-zero statistical power, severe over-fitting, and non-generalizable decision boundaries. Minimum threshold: $\ge 100$ verified attendance logs per clinician.
- **Remediation Strategy:**  
  Implement the classification pipeline with class-weight balancing and ROC-AUC metrics. Expose `status: "insufficient_data"` in the live prediction API until clinician QR check-ins cross the minimum statistical sample threshold.

### 3.3 Model 3: Appointment Consultation Duration Prediction
- **Required Target Definition:**  
  $$D_i = t_{\text{consultation\_complete}} - t_{\text{consultation\_start}}$$
- **Database Findings:**  
  The database records nominal `Doctor.consultationDuration = 30` minutes, but records zero empirical completion timestamps.
- **Data Quality Verdict:**  
  **MISSING TARGET LABELS.** 
- **Remediation Strategy:**  
  Add `consultationStartedAt` and `consultationCompletedAt` to `Appointment` model in Prisma. Implement the duration regression pipeline and return `status: "insufficient_data"` on production queries until completed consultations are logged.

### 3.4 Model 4: Department Demand Forecasting
- **Required Target Definition:**  
  $$Y_{\text{dept}, t} = \sum \text{Bookings}_{\text{dept}} \text{ on date } t$$
- **Database Findings:**  
  76 appointments spanning 16 calendar days across 9 departments ($\approx 0.52$ bookings per department per day).
- **Data Quality Verdict:**  
  **LIMITED TIME-SERIES HORIZON.** Multi-step autoregressive models (lag-1, lag-7, lag-14) require at least 60 to 90 consecutive operational days to establish seasonal periodicity.
- **Remediation Strategy:**  
  Implement moving-average baseline and time-series feature engineering. Expose moving-average trend while marking autoregressive ML forecasting as `status: "insufficient_data"`.

```

│                   Prospective Data Capture Protocol                    │

│ 1. Patient Reception Scan:                                             │
```
